## 1. บทสรุปสำหรับผู้รับมอบ

ระหว่างวันที่ 7–8 พฤศจิกายน 2569 ได้มีการต่อยอดงานบนบรานช์ `feature/gis-data-management`
เพื่อให้ระบบสามารถทำงานกับฐานข้อมูลที่ไม่ใช่ sandbox ในเครื่องได้ รวม 6 commit
บนบรานช์ใหม่ชื่อ `gis-unlock`

การเปลี่ยนแปลงทั้งหมดคงพฤติกรรมเดิมของ sandbox ไว้ครบถ้วน และ**ไม่ต้องแก้ไขสคริปต์
ใน `dev/` แม้แต่ไฟล์เดียว** อย่างไรก็ตามมีผลข้างเคียงหนึ่งข้อที่ต้องดำเนินการ (ข้อ A1)

งานที่ส่งมอบในเอกสารฉบับนี้คือเรื่องที่**ต้องใช้ความเข้าใจในสิ่งที่ผู้รับมอบออกแบบไว้เอง**
จึงไม่สามารถมอบหมายให้ผู้อื่นตัดสินใจแทนได้

### 2.2 ผลข้างเคียงที่ต้องดำเนินการ — sandbox เดิมใช้ต่อไม่ได้

migration 027 ถูกแก้ไข ส่งผลให้ค่า checksum ที่ตรึงต่อกันเป็นลูกโซ่ต้องคำนวณใหม่
ทั้งหมด ไฟล์ที่ได้รับผลกระทบ

```
migrations/ 027, 030, 031, 032, 033, 034, 035, 036, 037, 038,
            039, 040, 041, 042, 043, 044, 045, 046, 047, 048
tests/      test_gis_migration_runner.py, test_gee_dashboard_processing.py
```

**สิ่งที่ต้องทำ** ตาราง `gis.schema_migrations` ใน sandbox T0 เดิมจะไม่ตรงกับไฟล์ใหม่
จึงต้องสร้าง T0 ขึ้นใหม่ **โค้ดและสคริปต์ของผู้รับมอบไม่ต้องแก้ไข** กระทบเฉพาะฐานข้อมูล

ตรวจสอบรายการที่เปลี่ยนได้ด้วย

```bash
git diff b9b5b3a HEAD -- green-area-backend/migrations
```

### 2.3 เหตุผลของการแก้ migration 027

`cluster_name` เป็นค่าตั้งระดับ postmaster ซึ่งกำหนดได้เฉพาะใน `postgresql.conf`
พร้อมการ restart บริการฐานข้อมูลแบบ Supabase Cloud จึงไม่สามารถตั้งค่านี้ได้

**หลักฐาน** นำ migration 027 ฉบับเดิมไปติดตั้งบน PostgreSQL 17 มาตรฐาน

```
ERROR: GIS_LOCAL_TARGET_REQUIRED
```

หลังแก้ไข ตัวรันจะประกาศ `gis.cluster_name` และ `gis.mode` เอง แล้วบันทึกลง
`gis.environment` โดย **การไม่ประกาศยังหมายถึง sandbox เหมือนเดิม** และ sandbox
ยังต้องพิสูจน์ตนเองกับ postmaster เช่นเดิม

ทดสอบบน container PostgreSQL 17 จำนวน 5 กรณี

| กรณี | ผล |
|---|---|
| ไม่ประกาศค่าใด + postmaster ไม่ใช่ sandbox | ปฏิเสธ |
| ประกาศ sandbox + postmaster ไม่ใช่ sandbox | ปฏิเสธ |
| ประกาศ project ref แต่ mode เป็น local | ปฏิเสธ |
| ไม่ประกาศค่าใด + postmaster เป็น sandbox (ทางเดิม) | ติดตั้งครบ 027–048 |
| ประกาศ cloud + ไม่มี `cluster_name` | ติดตั้งครบ 027–048 |

## 3. ปัญหาที่ตรวจพบ พร้อมหลักฐาน

### 3.1 การ merge `78f0219` ไม่ใช่การปรับค่า hash แต่กระทบโครงสร้างที่ถูกอ่านด้วย AST

commit `78f0219` บน `main` (แก้ไขข้อผิดพลาดการวัด 4 รายการ) ปรับโครงสร้างของโค้ดที่
`gis_worker/processing_provider.py` อ่านค่าด้วย `ast` ในช่วงบรรทัด 145–190

| จุดตรวจ | รูปแบบที่ตัวอ่านคาดหวัง | รูปแบบหลัง merge |
|---|---|---|
| `_mask_landsat_clouds` | `bitwiseAnd(1 << n)` | `bitwiseAnd(_LANDSAT_CLOUD_BITMASK)` ซึ่งไม่ใช่ `ast.BinOp` |
| `S2_CLOUD_FILTER_PCT` ใน `compute.py` | ค่าคงที่ระดับโมดูล | เปลี่ยนเป็น `from gee_utils import ...` |
| ฟิลเตอร์เมฆใน `_compute_ndvi_monthly` | `CLOUDY_PIXEL_PERCENTAGE` ภายในฟังก์ชัน | ย้ายไปอยู่ใน `s2_clean_collection()` |

นอกจากนี้ค่าทางวิทยาศาสตร์เปลี่ยนจริง ได้แก่ bit สำหรับ mask เมฆของ Landsat
จาก `(3, 4)` เป็น `(1, 2, 3, 4)` ขณะที่ `method_registry.py` ประกาศไว้ว่า
`lst_mask_bits: (3, 4)`

**ประเด็นที่ต้องตัดสินใจ** ค่าที่แก้ไขให้ถูกต้องแล้ว ยังถือเป็น `legacy-v1` อยู่หรือไม่
หรือต้องกำหนดเป็นเวอร์ชันวิธีคำนวณใหม่

**ข้อควรระวัง** `78f0219` ยังไม่ได้อยู่ในสายของ `gis-unlock` (ตรวจด้วย
`git merge-base --is-ancestor`) ค่า hash ที่ตรึงไว้จึงยังตรงกับไฟล์บนบรานช์
**ห้ามปรับค่า hash ก่อน merge** เพราะจะทำให้ชุดทดสอบไม่ผ่านโดยไม่จำเป็น

### 3.2 การประมวลผล GEE จริงถูกปิดไว้ในระดับโครงสร้างฐานข้อมูล

ค่าที่บ่งชี้ว่าการประมวลผลจริงยังไม่ได้รับอนุมัติ ปรากฏในหลายตำแหน่ง

```
migrations/035, 043, 044, 045   กำหนด 'live_enabled', false ในผลลัพธ์ readiness
migrations/045                  ค่าตั้งต้นของระเบียนความปลอดภัยเป็น kind: "unapproved"
gis_worker/gee_execution_safety.py:33   live_enabled: Literal[False] = False
routers/gis.py:76                       result['gee_live_enabled'] = False
```

และ worker ทุกตัวกำหนดให้ค่านี้ต้องเป็น `False` จึงจะยอมทำงาน

**ประเด็นที่ต้องตัดสินใจ** จะเปิดการประมวลผลจริงที่เผยแพร่ผลได้เมื่อใด ผู้ใดเป็น
ผู้อนุมัติ และต้องใช้หลักฐานใดประกอบ ตราบที่ยังไม่ตัดสินใจ ระบบจะให้ผลเฉพาะแบบ
สังเคราะห์เท่านั้น ไม่ว่าจะติดตั้งที่ใด

### 3.3 worker จำนวน 5 รายการผูกกับโหมด `local_synthetic`

ไฟล์ `processing_worker.py`, `ldd_worker.py`, `ldd_prepare_worker.py`,
`geotiff_worker.py`, `geotiff_prepare_worker.py` กำหนดเงื่อนไข
`mode != 'local_synthetic'` ให้ปฏิเสธการทำงาน

เนื่องจาก migration 027 ผูก `cluster_name` กับ `mode` ไว้ด้วยกัน
(`CHECK ((cluster_name='green-area-gis-t0') = (mode='local_synthetic'))`)
ฐานข้อมูลบนคลาวด์จะมี `mode = 'cloud'` เสมอ worker ทั้งห้าจึงปฏิเสธการทำงานเสมอ

**ประเด็นที่ต้องตัดสินใจ** worker ใดควรทำงานบนคลาวด์ และ worker ใดควรทำงานเฉพาะ
ใน sandbox ตามเจตนาเดิม

**ข้อควรระวัง** การแก้เพียงค่า `cluster_name` ในไฟล์เหล่านี้ จะทำให้ระบบดูเหมือน
พร้อมใช้งานแต่ยังปฏิเสธที่เงื่อนไข `mode` และ `live_enabled` อยู่ดี ซึ่งจะทำให้
ผู้ตรวจสอบภายหลังเสียเวลาค้นหาสาเหตุ

## 5. เรื่องที่ควรทราบเพิ่มเติม

ระบบตรวจอัตโนมัติ (CI) ของคลังโค้ดไม่เคยทำงานกับบรานช์นี้มาก่อน เนื่องจากตั้งค่าให้
ตรวจเฉพาะการผลักขึ้น `main` และการเปิด pull request ซึ่งบรานช์นี้ยังไม่เคยเปิด

เมื่อนำมาทดลองรันจริง พบว่าไม่ผ่านทุกขั้นตอน และได้ดำเนินการแก้ไขแล้ว

| ขั้นตอน | ก่อน | หลัง |
|---|---|---|
| `ruff check .` | ไม่ผ่าน 769 รายการ | ผ่าน |
| `pytest tests/` | หยุดตั้งแต่ขั้นรวบรวมไฟล์ | ผ่าน |
| `eslint src --max-warnings 0` | ไม่ผ่าน 1 ข้อผิดพลาด 2 คำเตือน | ผ่าน |

ในจำนวน 769 รายการ มี 714 รายการเป็นรูปแบบการเขียนแบบรวบรัด (E701/E702)
ซึ่ง**ไม่ได้ปรับแก้โค้ด** แต่ประกาศข้อยกเว้นไว้ใน `ruff.toml` พร้อมเหตุผล
ส่วนอีก 55 รายการเป็นการ import ที่ไม่ได้ใช้งาน ได้นำออกแล้ว

นอกจากนี้ชุดทดสอบ `test_real_credentials_and_live_egress_cannot_be_enabled` ตรวจสอบ
สถานะระดับโปรเซส ซึ่ง `tests/test_canopy.py` (ชุดทดสอบของเว็บหลัก ไม่เกี่ยวกับ GIS)
ได้ import `earthengine-api` ไว้ก่อนแล้ว จึงปรับให้ตรวจใน interpreter ใหม่แทน

ตั้งแต่บัดนี้ CI จะตรวจทุกครั้งที่ผลักขึ้นบรานช์ `feature/**` และ `gis-**`
