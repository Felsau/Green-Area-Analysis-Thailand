## 3. รายละเอียดงาน

### W2. เขียนตัวติดตั้ง migration สำหรับฐานข้อมูลภายนอก

**สิ่งที่ต้องทำ** เขียนสคริปต์เดียวที่ติดตั้ง migration หมายเลข 027 ถึง 048 เรียงตามลำดับ
ลงฐานข้อมูลเปล่า แล้วบันทึกรายการลงตาราง `gis.schema_migrations`

**เหตุผล** ปัจจุบันขั้นตอนนี้กระจายอยู่ในไฟล์ `dev/gis_local/*_local.py` ประมาณ 8 ไฟล์
โดยแต่ละไฟล์ฝังหมายเลขเวอร์ชันของตัวเองไว้ ยังไม่มีตัวรันเดียวที่ครอบคลุมทั้งชุด

**สิ่งที่ทดสอบมาแล้วและใช้เป็นจุดตั้งต้นได้**

1. ก่อนรันเนื้อของแต่ละ migration ต้องประกาศค่าแบบ session-local สี่รายการ

```sql
SELECT set_config('gis.runtime_instance',      '<hex ตัวพิมพ์เล็ก 32 ตัว>', true);
SELECT set_config('gis.baseline_fingerprint',  '<hex ตัวพิมพ์เล็ก 64 ตัว>', true);
SELECT set_config('gis.cluster_name',          '<project-ref>', true);
SELECT set_config('gis.mode',                  'cloud', true);
```

2. การไม่ประกาศสองค่าหลัง หมายถึง sandbox ในเครื่อง ซึ่งเป็นพฤติกรรมเดิมที่ต้องคงไว้
3. ทุกไฟล์ต้องปิดท้ายด้วยการบันทึก ledger ในฐานะ `gis_owner`

```sql
SET LOCAL ROLE gis_owner;
INSERT INTO gis.schema_migrations(version, sha256) VALUES (<เลข>, '<sha256 ของไฟล์>');
RESET ROLE;
```

4. `sha256` คือค่าแฮชของไฟล์ทั้งไฟล์ ไม่ใช่เฉพาะบางส่วน
5. ฐานข้อมูลเปล่าจะยังไม่มี role และตารางที่ migration อ้างถึง ต้องเตรียม
   `gis_owner`, `gis_worker`, `gis_native_worker`, `authenticator` และตาราง
   `public.districts` ตาม migration หมายเลข 007 ไว้ก่อน มิฉะนั้นจะติดกลางทาง

**วิธีทดสอบ** ไม่ต้องใช้โปรเจกต์จริง ใช้ PostgreSQL 17 ในคอนเทนเนอร์เปล่า ๆ ก็พอ

```
docker run -d --name pgtest -e POSTGRES_PASSWORD=... postgres:17
```

**เกณฑ์ว่าเสร็จ** ติดตั้งลงฐานข้อมูลเปล่าได้ครบตั้งแต่ 027 ถึง 048 และเมื่อเรียก
`gis_readiness()` แล้วได้ค่า `cluster_name` กับ `mode` ตรงกับที่ประกาศไว้

> **ยังไม่ต้องชี้ไปที่โปรเจกต์ Supabase จริง**
> ตรวจแล้วว่าโครงการพร้อมในแง่รุ่นและสิทธิ์ (ดูข้อ 4) แต่ฐานข้อมูลนั้นมีผู้ใช้จริงอยู่
> การติดตั้งจริงต้องให้เจ้าของโครงงานกำหนดเวลาเอง งานสัปดาห์นี้คือทำให้ตัวติดตั้ง
> ทำงานถูกต้องในที่ปลอดภัยก่อน

### W3. แยกชั้นจัดเก็บไฟล์ออกจากดิสก์

**สิ่งที่ต้องทำ** แยกส่วนที่อ่านและเขียนไฟล์ใน `gis_ldd_storage.py` และ
`gis_geotiff_storage.py` ออกมาเป็นชั้นเดียว โดยให้การเขียนลงดิสก์แบบเดิมเป็นค่าตั้งต้น
**พฤติกรรมต้องไม่เปลี่ยนแม้แต่นิดเดียว**

**เหตุผล** ไฟล์ที่ผู้ใช้อัปโหลดถูกเก็บลงดิสก์ของเครื่องพร้อมไฟล์ `owner.json` กำกับ
ความเป็นเจ้าของ เมื่อนำขึ้นโฮสต์อย่าง Render ดิสก์จะถูกล้างทุกครั้งที่เริ่มระบบใหม่
ถ้ายังไม่แยกชั้นนี้ออกมา การย้ายไปเก็บที่อื่นจะต้องรื้อหลายจุดพร้อมกัน

**ขอบเขตที่ชัดเจน** ทั้งสองไฟล์รวมกันประมาณ 340 บรรทัด มีจุดที่แตะดิสก์ตรง ๆ 13 จุด
และมีชุดทดสอบคุมอยู่แล้วคือ `tests/test_ldd_upload_api.py` และ
`tests/test_geotiff_upload_api.py`

**ข้อห้ามที่สำคัญที่สุด** ห้ามตัดการตรวจสอบค่า hash ออกเพื่อความสะดวก ระบบตรวจทุกครั้ง
ที่อ่านไฟล์ และรายงานรหัส `GIS_LDD_INTEGRITY` เมื่อไม่ตรง กลไกนี้ต้องอยู่ครบ

**เกณฑ์ว่าเสร็จ** ชุดทดสอบเดิมผ่านทั้งหมดโดยไม่ต้องแก้ไฟล์ทดสอบ

> **ยังไม่ต้องเขียนตัวเก็บแบบใหม่ และยังไม่ต้องเลือกว่าจะไปเก็บที่ไหน**
> สัปดาห์นี้ขอแค่แยกชั้นให้เรียบร้อย การเลือกที่เก็บเป็นการตัดสินใจของเจ้าของโครงงาน

### W4. สำรวจชื่อฟิลด์ของไฟล์ LDD จริงรายจังหวัด

**สิ่งที่ต้องทำ** เปิดไฟล์ shapefile ของกรมพัฒนาที่ดินอย่างน้อย 3 จังหวัด แล้วทำตาราง
ว่าแต่ละจังหวัดมีฟิลด์ชื่ออะไรบ้าง ค่าเป็นแบบไหน และ encoding เป็นอะไร จากนั้นเสนอว่า
ระบบควรรับฟิลด์อย่างไรจึงจะครอบคลุมทุกจังหวัด **ไม่ต้องแก้โค้ด**

**เหตุผล** ขณะนี้ระบบรับไฟล์ LDD ได้เพียงรูปแบบเดียว

```
gis_worker/ldd_provider.py:36
REQUIRED_FIELDS = ('LUL1_CODE', 'LU_CODE', 'Shape_Area')
```

บรรทัดที่ 597 บังคับให้ไฟล์ต้องมีครบทั้งสามชื่อ มิฉะนั้นจะปฏิเสธด้วยรหัส
`ATTRIBUTES_MISSING` และบรรทัดที่ 70 บังคับให้คำขอต้องระบุชื่อทั้งสามนี้ตรงกันด้วย

จากการสำรวจไฟล์จริง 6 จังหวัดเมื่อเดือนกันยายน พบว่า **ไม่มีจังหวัดใดเลยที่มีฟิลด์ชื่อ
`Shape_Area`** จังหวัดอื่นใช้ `Area_Sqm`, `Area_Rai` หรือ `Area_RAI` แทน และ
`LUL1_CODE` หายไปในครึ่งหนึ่งของจังหวัดที่ตรวจ

**ผลที่ตามมา** ระบบจัดการข้อมูล LDD ในขณะนี้รับได้เฉพาะไฟล์กรุงเทพมหานคร ปี 2566
เพียงไฟล์เดียวในโลก

**สิ่งที่ต้องส่ง** ตารางเปรียบเทียบรายจังหวัด และข้อเสนอว่าควรรับฟิลด์อย่างไร

**เกณฑ์ว่าเสร็จ** มีตารางที่อ้างอิงไฟล์จริง ระบุชื่อจังหวัดและปีของไฟล์ที่เปิดดู

> **ยังไม่ต้องแก้ `ldd_provider.py`** ไฟล์นั้นถูกตรึงค่า sha256 ไว้ใน
> `dev/gis_local/gee-runtime-image.lock.json` ในฐานะซอร์สที่ผ่านการตรวจแล้ว
> การแก้ต้องทำพร้อมกับปรับ lock และต้องหารือกับผู้พัฒนาเดิมก่อน

## 4. ผลการตรวจสอบฐานข้อมูล Supabase (ตรวจแล้ว ไม่ต้องทำซ้ำ)

เดิมรายการนี้เป็นงาน W1 ตรวจเสร็จแล้วเมื่อ 8 พฤศจิกายน 2569 ด้วยคำสั่งใน SQL Editor
ของโครงการ ผลเป็นดังนี้

| สิ่งที่ตรวจ | ผล |
|---|---|
| รุ่นของฐานข้อมูล | PostgreSQL 17.6 (`server_version_num` = 170006) |
| ผ่านเงื่อนไขของ migration 027 (`>= 170000`) | **ใช่** |
| ผู้ใช้ที่เชื่อมต่อ | `postgres` |
| เป็น superuser หรือไม่ | ไม่ใช่ |
| สร้าง role ได้หรือไม่ (`rolcreaterole`) | **ได้** |

ตรวจเพิ่มเติมในไฟล์ migration ทั้ง 20 ไฟล์ว่ามีคำสั่งใดที่ต้องใช้สิทธิ์ superuser หรือไม่
**ไม่พบ** ไม่มี `CREATE EXTENSION`, `ALTER SYSTEM`, `CREATE EVENT TRIGGER` หรือ
`CREATE LANGUAGE` เลย ส่วน `CREATE ROLE` ที่มีอยู่ 6 จุดใช้สิทธิ์ `rolcreaterole`
ซึ่งบัญชีนี้มีอยู่แล้ว

**สรุป** ฐานข้อมูลของโครงการพร้อมรับ migration 027 ถึง 048 ในแง่ของรุ่นและสิทธิ์

## 5. งานที่เคยอยู่ในรายการ แต่ตรวจสอบแล้วว่าไม่ต้องทำ

ก่อนส่งมอบได้ตรวจสอบซ้ำ และพบว่าสองรายการต่อไปนี้ทำเสร็จไปแล้ว จึงตัดออก

1. **บันทึกค่า digest ของ image ลงคลังโค้ด** ไฟล์ `dev/gis_local/images.lock.json`
   มีอยู่แล้ว ระบุชื่อ repository, digest, รุ่นที่ตรวจแล้ว และลิงก์ต้นทางครบทั้งสี่ตัว
   และ `dev/gis_local/manage.py` อ่านไฟล์นี้ไปใช้เอง ทดสอบแล้วว่า image ทั้งสี่ตัว
   ยังดึงจาก registry สาธารณะได้จริง
2. **สร้าง Dockerfile ของ worker** ทำให้แล้วที่
   `green-area-backend/gis_worker/Dockerfile` ทดสอบแล้วว่าภายใน image นั้น
   ชุดทดสอบ native ผ่าน **198 รายการ ไม่มีข้ามสักข้อ** รวมถึงข้อที่ตรวจว่าผลลัพธ์
   ตรงกับค่าที่ตรึงไว้ทุกไบต์ ซึ่งถูกข้ามบนเครื่องอื่นทุกเครื่อง และระบบตรวจอัตโนมัติ
   ตรวจซ้ำให้ทุกครั้งที่มีการส่งโค้ดแล้ว

## 6. งานที่ยังไม่ส่งมอบในรอบนี้

รายการต่อไปนี้อยู่ในแผนระยะถัดไป **กรุณายังไม่เริ่มดำเนินการ**

1. การนำตัวติดตั้ง migration ไปใช้กับโปรเจกต์ Supabase จริง
2. การเขียนตัวเก็บไฟล์แบบใหม่ และการเลือกว่าจะไปเก็บที่ใด
3. การแก้ `ldd_provider.py` ให้รับฟิลด์หลายรูปแบบ

ข้อแรกเป็นการแก้ฐานข้อมูลที่มีผู้ใช้จริงอยู่ จึงต้องให้เจ้าของโครงงานเป็นผู้ตัดสินใจและ
กำหนดเวลาเอง ไม่ใช่งานที่ทำได้เองในสัปดาห์นี้
