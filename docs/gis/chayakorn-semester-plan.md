## A. ขอบเขตงานของฉัน (ตาม PDF หน้า 1)

1. **GIS Upload / Validation:** LDD Shapefile ZIP, GeoTIFF, CRS, Geometry, Attributes, Field Profiles, Encoding และการตรวจข้อมูลจริง.
2. **GIS Dataset Management:** Dataset/Edition, ตรวจสอบ, Preview, เปิดใช้, ถอนใช้ และย้อนกลับข้อมูลอย่างไม่ทำลายฉบับเดิม.
3. **Integration:** เชื่อมระบบจัดการ GIS กับ Frontend, FastAPI, Supabase และ Dashboard เดิม; ไม่ทำให้ NDVI/LST เดิมหยุดทำงาน.
4. **Processing:** Google Earth Engine, NDVI/LST, Background Jobs, History/Status, Cache และผลที่แสดงใน Dashboard.
5. **Deployment / QA:** ทดลองบนหลายเครื่อง เตรียมเซิร์ฟเวอร์ทดลอง และเซิร์ฟเวอร์ผู้ทดสอบภายใต้การอนุมัติ.
6. **User Testing / Bug Fix:** แก้ปัญหาที่ผู้เชี่ยวชาญและผู้ใช้พบในส่วนที่ได้รับมอบหมาย.
7. **Handover:** คู่มือผู้ใช้/ผู้ดูแล ระบบที่ส่งมอบและเอกสารเทคนิค.

**ไม่ใช่หน้าที่หลักของฉัน:** การบริหารทีม/นัดประเมิน/ตรวจรับ (หัวหน้ากลุ่ม), การจัดทำบทที่ 4–5 และวิเคราะห์แบบประเมิน (สมาชิกคนที่ 3) เว้นแต่ได้รับมอบหมายชัดเจน.

## E. กฎรายงานต่อหัวหน้าทุกวันศุกร์

ทุก Task ต้องลงบอร์ด **ชื่องาน / เจ้าของ / สิ่งส่งมอบ / วันกำหนดส่ง** และเมื่อส่งรายงานต้องระบุ:

1. Week, ช่วงวันที่, วันที่รายงาน, งานที่ได้รับมอบหมายจริง.
2. งานที่ **DONE & VERIFIED**, **IN PROGRESS**, **BLOCKED**, **NOT STARTED** แยกให้ชัด.
3. ไฟล์/โมดูล/Commit/PR/Diff ที่เปลี่ยน **เฉพาะที่เกิดจริง**.
4. ผลทดสอบ (คำสั่ง/สภาพแวดล้อม/จำนวน PASS-FAIL) พร้อมลิงก์ Log หรือ Screenshots.
5. การทดสอบ Synthetic เทียบกับ Real Data และ Local เทียบกับ Live/Deployed ห้ามปนกัน.
6. ปัญหา/ความเสี่ยง/ข้อจำกัด/ผลกระทบต่อกำหนดเดิม.
7. สิ่งที่ต้องให้หัวหน้าตรวจรับหรืออนุมัติ.
8. งานสัปดาห์หน้าและกำหนดส่งใหม่หากล่าช้า.

**กระบวนการรายสัปดาห์:** จันทร์รับงานและสรุปมติประชุม → พุธอัปเดต Blocker → พฤหัสตรวจผล/รวบรวมหลักฐาน → ศุกร์ส่งรายงานให้หัวหน้า โดยส่งรายงานแม้ Task ยังไม่เสร็จ.

## F. สถานะและข้อจำกัดที่ทราบก่อนเริ่มแผน (จากรายงาน Audit 6 พ.ย. 2569 ไม่ใช่ผลตรวจใหม่)

ใช้เป็น **รายการให้ตรวจสถานะ Source ล่าสุดก่อนจัดคิวงาน** ไม่ใช่ยืนยันว่ายังค้างทุกข้อ:

- ระบบ Dataset/Edition/Upload/GeoTIFF/Queue/Preview/Publication มี Implementation และ Local/Synthetic Tests แต่ Browser E2E ใน Source ล่าสุดยังไม่ครบ.
- Upload ZIP แล้วผู้ใช้ไม่เห็น Feedback ชัดเจน (อาจปิด Modal และ Error ไปอยู่ด้านบน).
- ข้อมูลจริงปทุมธานี 2568 มี Multi-Shapefile ZIP, เอกสารประกอบ, Encoding `ANSI 874`, Fields `Area_Sqm` / `LU_ID_L1` / `LU_CODE`, Legend และ Boundary ที่ต้องทบทวน.
- LDD Validation v2 ต้องทบทวน SQL Migration ถัดไป (Audit ก่อนหน้าพบล่าสุด 048, 049 ยังไม่ปรากฏ); ตรวจปัจจุบันก่อนตัดสินใจ.
- GEE Dashboard Job สำเร็จไม่ได้แปลว่า Cache ที่ถูกต้องมีอยู่เสมอ; มีความเสี่ยง Timeout/Lost Lease และการเขียน Cache ภายหลัง.
- Genuine Live GEE ที่ต้องอาศัย Recorder/Restricted Egress ยังไม่ได้รับรองพร้อมใช้งานจากหลักฐานเดิม.
- Local Demo Launcher เคยรายงาน `LOCAL_DEMO_FAILED`; ต้องพิสูจน์ว่ารันซ้ำได้.

**ลำดับเสนอสำหรับ W2–W5 (เป็นคำแนะนำเพิ่มเติม ไม่ใช่ข้อความ PDF):**
1. ปิดงานที่กำลังทำ/เก็บ Evidence และตรวจ Git status ไม่รบกวน Agent อื่น.
2. ทำ Upload Error Feedback และ Demo Startup ให้ทดสอบซ้ำได้.
3. ตรวจ Cross-platform Integrity + NDVI/LST Formula Versioning และ Integration กับโค้ดระบบหลัก.
4. ทดสอบ LDD จากข้อมูลจริง (กรุงเทพฯ และจังหวัดอื่น) โดยไม่ลดเกณฑ์ Validation แบบไม่มีหลักฐาน.
5. ตรวจและอนุมัติ SQL/Review Workflow ก่อนใช้ LDD Prepare v2; ทดสอบ Activate/Withdraw/Rollback และ Dashboard Data Provenance.

## G. กฎสำหรับ Claude Code

1. อ่านแผนนี้ร่วมกับข้อกำหนดโครงงาน รายงานต้นฉบับ และคำสั่งโครงการที่ใช้อยู่ **ก่อนจัดลำดับงาน**.
2. แผนเป็น **Schedule/Backlog** ไม่ใช่ Authorization ให้ Deploy, Apply Migration, เปิด Live GEE, แก้ Cloud IAM/Billing, Commit/Push หรือเปลี่ยน Branch.
3. ก่อนทำ Task ใด ตรวจ Source ล่าสุด, Existing Tests, Git status และยืนยันขอบเขตที่ได้รับอนุมัติ; อย่าแก้ทับไฟล์ที่ Agent อื่นกำลังทำ.
4. รักษา Legacy Data/Methods/Cache และตรวจ Regression/Boundary/SQL/RLS ตามระดับความเสี่ยง.
5. ชี้แจงความแตกต่างของ `implemented`, `synthetic tested`, `real-data tested`, `local E2E`, `GEE live verified` และ `production ready`.
6. เมื่อจบ Task รายงานสิ่งที่แก้ Files/Diff/Tests/Remaining และเชื่อมกับ Week/Deliverable.
7. เมื่อผู้ใช้สั่ง **"สรุปรายงานวันศุกร์"** ให้จัดทำรายงานตามข้อ E ด้วยหลักฐานที่ตรวจได้จริงและให้ผู้ใช้ส่งหัวหน้าเอง.
8. หากแผนขัดกับความปลอดภัย งบประมาณ หรือขอบเขตรายงาน ให้แจ้งเป็น Blocker พร้อมทางเลือกแทนการข้าม Guard.
9. **อย่าเริ่มทำงานรายสัปดาห์ทั้งหมดเพียงเพราะอ่านไฟล์นี้** และอย่าถือว่าหมายเลขสัปดาห์เป็นอนุมัติงาน.
