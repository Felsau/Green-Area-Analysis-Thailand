# W7 ขอบเขตของ `legacy-v1` (8 พ.ย. 2569 · เลือกทางที่ 2 แล้ว ดูหัวข้อ 5)

ผู้จัดทำร่าง: ชยากร (ผู้พัฒนาบรานช์ `feature/gis-data-management`) · เอกสารนี้ไม่แก้โค้ดและไม่รวมบรานช์

## 1. ข้อเท็จจริง
- **ยังไม่ได้ตรวจตัว commit `78f0219`**: ไม่มีในเครื่องหลัง `git fetch origin` และ `origin/main` (`048273f`) ยังใช้ `bitwiseAnd(1 << 4)` กับ `bitwiseAnd(1 << 3)` · เนื้อหาของ `78f0219` ในข้อนี้จึงมาจากเอกสารส่งมอบฉบับที่ 2 เท่านั้น (บิต (3,4) → (1,2,3,4), LST ขยับ +0.10 ถึง +0.43 °C, โครงสร้างเปลี่ยน 3 จุด)
- `gis_worker/method_registry.py`: `legacy-v1` ครอบ 4 เวอร์ชัน (`ndvi-annual|ndvi-monthly|lst-annual|lst-monthly-legacy-v1`) · ผูก hash ของ `gee_utils.py`, `routers/ndvi/compute.py`, `routers/lst.py` และค่า `lst_mask_bits = (3, 4)`
- กฎในไฟล์เดียวกันและใน `docs/gis/method-review-contract.md`: นิยามที่อนุมัติแล้ว**แก้ไม่ได้** · ผลและ cache เก่าผูกกับนิยามที่ใช้คำนวณ **ไม่มีการเปลี่ยนป้าย** · นิยามใหม่ต้องมี forward migration เพราะ SQL ปักหมุด `legacy-v1` ไว้
- SQL ที่ปักหมุดอยู่: 035 เก็บ hash ของซอร์สทั้งสามไฟล์ (`legacy_pipeline_sha256`, แบบ v0) · 044 `gis.gee_live_method()` ฝังนิยาม LST ทั้งรายปีและรายเดือนว่า `"qa_mask_bits":[3,4]`
- `processing_provider.legacy_spec()` อ่านซอร์สด้วย `ast` และบังคับรูปแบบ `bitwiseAnd(1 << n)`, ค่าคงที่ `S2_CLOUD_FILTER_PCT` ระดับโมดูล, และฟิลเตอร์ `CLOUDY_PIXEL_PERCENTAGE` ภายใน `_compute_ndvi_monthly` · ซอร์สที่ไม่ตรงจะล้มด้วย `PROCESSING_LEGACY_SOURCE_CHANGED` หรือ `PROCESSING_LEGACY_SPEC_INVALID`
- งานที่บันทึกแล้วเก็บชื่อ `method_version` และ identity ที่ปักหมุดไว้ · คำขอที่ identity ไม่ตรงกับนิยามบนดิสก์จะล้มด้วย `PROCESSING_METHOD_UNREVIEWED` (ตรวจจากโค้ดเท่านั้น ไม่ได้ query ฐานข้อมูล จึงไม่รู้จำนวนงานเก่า)

## 2. เทียบสองทาง

| | ทางที่ 1 ยังเป็น `legacy-v1` | ทางที่ 2 วิธีใหม่ `legacy-v2` |
|---|---|---|
| ค่าใน registry | แก้ `lst_mask_bits` และ hash ซอร์สของนิยามเดิม | เพิ่มนิยามใหม่ นิยามเดิมไม่แตะ |
| SQL ที่ปักหมุด (035, 044) | ต้องแก้ไฟล์ที่ apply แล้ว หรือออก migration ที่เขียนทับความหมายของ `legacy-v1` | forward migration เพิ่มนิยาม v2 อย่างเดียว |
| งานเก่า | ชื่อเดียวกันแต่ตัวเลขคนละชุด สืบย้อนไม่ได้ว่าใช้บิตไหน | ยังบอกได้ว่าคำนวณด้วยบิต (3,4) |
| ขัดกับกฎ registry | ขัด (แก้นิยามที่อนุมัติแล้ว, เปลี่ยนป้าย) | ไม่ขัด |
| งานที่ต้องทำ | น้อยกว่า | มากกว่า: นิยามใหม่ + ตัวอ่าน `ast` + migration + เทสต์ |

## 3. ข้อแนะนำ
เลือก **ทางที่ 2** เพราะเป็นทางเดียวที่ไม่ขัดกับกฎที่ระบบตั้งไว้เอง และไม่ต้องแก้ migration ที่ apply แล้ว
ส่วนตัวเลขที่ต่างกันสูงสุด 0.43 °C ก็มากพอที่ต้องแยกให้รู้ว่าผลแต่ละชุดคำนวณด้วยวิธีไหน

## 4. ถ้าเลือกทางที่ 2
- ชื่อ: method_id `legacy-v2` · เวอร์ชัน `ndvi-annual-legacy-v2`, `ndvi-monthly-legacy-v2`, `lst-annual-legacy-v2`, `lst-monthly-legacy-v2`
  (NDVI ต้องขึ้น v2 ด้วย แม้ค่าทางวิทยาศาสตร์ไม่เปลี่ยน เพราะ hash ของซอร์สที่ใช้ร่วมกันเปลี่ยนตาม `78f0219`)
- งานเก่า: ผลและ cache ที่เป็น `legacy-v1` คงไว้ตามเดิม ไม่คำนวณซ้ำและไม่เปลี่ยนป้าย · คำขอ `legacy-v1` ที่ยังค้างในคิวหลังรวมบรานช์จะล้มด้วย `PROCESSING_METHOD_UNREVIEWED` ให้ส่งใหม่เป็น v2 ·
  การแสดงผลที่เทียบหลายปีต้องบอกชื่อวิธีของแต่ละค่า · ต้องตรวจอีกครั้งว่า `78f0219` เพิ่ม `cache_version` ของ cache LST เดิมหรือไม่ (ยังไม่ได้ตรวจ)
